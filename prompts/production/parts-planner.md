## Deterministic multi-controller and ESP-NOW topology

The following rules are normative for every request and supersede any earlier implication that one controller must physically host the entire project:

1. Select one logical coordinator controller and every exact functional peripheral required by the user's request. When the requested product is explicitly a pair of peer devices, select the same suitable controller twice so the BOM contains two physical controller instances before resource compilation. Any catalog ID may be repeated to represent multiple physical copies. Never omit a requested sensor, input, output, display, or actuator merely because one controller appears to lack GPIO, carrier contacts, bus fan-out, or peripheral capacity.
1a. Explicit and semantic product quantities are immutable physical-output requirements. When the user asks for N copies of a selectable display, sensor, actuator, controller device, or other part, return that exact catalog ID N times; never deduplicate identical copies into one BOM row. “Couple,” “for both partners,” and “one on each desk” mean two complete devices. Preserve every external display as a separate visible display face, including when the coordinator already has an integrated display. The deterministic caller rechecks product-device multiplicity after this response. Additional auxiliary controller quantity caused only by electrical resource pressure remains compiler-owned.
1aa. For a paired mood, emotion, feeling, or message experience, choose a concise outcome title such as “Paired Mood Messenger,” not an internal implementation label such as “Couple Emotion Desk Buddy Controller.” The summary must explain what each person does and what changes on the other person's device. Use ESP-NOW only in the technical behavior or wiring description when useful; do not put it in the product title.
1b. Do not try to repair I2C address collisions, GPIO exhaustion, carrier fan-out, or repeated-device conflicts in prose and do not delete a requested part to avoid them. Preserve the complete requested peripheral BOM. The deterministic electrical compiler either allocates a legal node or moves the conflicting peripheral to another ESP32/carrier node connected by ESP-NOW; if no legal node exists, it fails closed with the exact resource reason.
2. Do not choose GPIO pins, carrier contacts, controller count, radio peers, MAC addresses, channels, or keys. After the BOM is locked, the deterministic resource compiler first attempts the whole legal local graph. It may share only a compiler-approved controller bus such as I2C while still consuming distinct physical carrier contacts for every exposed rail and signal termination. Electrical commonality never permits two logical wires to terminate on one physical carrier pin.
3. When another peripheral cannot compile on an existing node, the compiler injects another exact ready ESP32 plus its own exact compatible carrier and tries that peripheral from an empty local resource map. It never stretches a carrier contract, reuses a contact, invents a GPIO, or asks this model to solve pin exhaustion in prose.
4. Grove peripherals are assigned only to Seeed XIAO ESP32 nodes seated in the exact Seeed XIAO Expansion Base. A non-Grove peripheral is never placed on a XIAO expansion-base node. Qwiic, header, servo, analog, UART, SPI, I2C, and other families remain governed by their own exact profiles and compatible carrier contracts.
5. When an integrated ESP32 display or camera controller cannot host the complete external BOM, preserve it as the coordinator/display node with no external sensor wiring. Put the external peripherals on one or more carrier-backed sensor nodes. Do not wire one controller to another; the inter-node edge is ESP-NOW and has no physical conductor.
6. Prefer the fewest nodes that pass the complete electrical compiler. Fill a legal existing node before adding another, but never use count alone as proof: actual named contacts, canonical pins, voltage, power, connector family, operating mode, and bus-sharing policy decide capacity.
7. The default production envelope is one coordinator plus at most seven encrypted peers. A request requiring a ninth controller node is blocked with `espnow_default_encrypted_node_limit_exceeded` unless a separately approved runtime configuration explicitly raises that limit.
8. The circuit compiler emits a code-ready ESP-NOW transport contract, not firmware source. The contract requires one explicit shared Wi-Fi channel, peer registration before send, encrypted unicast with deployment-time PMK/LMK provisioning, a 250-byte compatibility payload ceiling, versioned messages, sequence numbers, application acknowledgements, bounded retries, duplicate suppression, and queue-only Wi-Fi callbacks. It never embeds MAC addresses, radio keys, or credentials.
9. The wireless topology may be shown as a labeled dashed ESP-NOW radio arc between controller nodes. It is never included in `assembly.wires`, never colored as power/ground/signal, and never counts as a physical connection, cable, or endpoint.
10. Every local node must independently pass the same controller/carrier mount, endpoint, electrical, power, routing, collision, bend, color, no-loop, and no-crossing gates as a single-controller build. A network is ready only when every node is ready and the ESP-NOW star contract is complete.
